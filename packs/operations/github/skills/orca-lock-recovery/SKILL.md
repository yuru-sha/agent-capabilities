# Recover an Orca automation lock

Use this Skill only for locks created by `issue-omp-handoff` or `issue-pr-lifecycle`. Both Automations share one lock per target repository. Never remove it just because it looks old or because another run reports that it is held.

## Resolve the exact run

1. Read `$HOME/.omp/automations/issue-omp-handoff/<repository-lock>/owner.json`. Require non-empty `run_id`, `automation_run_id`, `parent_worktree_id`, `repository`, `automation_key`, `acquired_at`, and `phase` fields. Match `repository` to the requested canonical identity and `automation_key` to exactly one of `issue-omp-handoff` or `issue-pr-lifecycle`. For `issue-pr-lifecycle`, `active_issue` must be `null` or an object containing `number`, exact `worktree_id`, phase, and ordered `pull_requests`. If present, `entry_state` must be a lifecycle entry label, and handoff run/Automation run/parent IDs must be valid. Older lock records may lack those newer fields; derive them from the Issue manifest, Orca worktree lineage, and exact handoff run as described below. If any required value is malformed or mismatched, stop and escalate.
2. Read the version-matched Orca guide with `orca skills get orca-cli --reference references/automations.md`. Use `orca automations list --json` and `orca automations show <automationId> --json` to identify exactly one Automation matching the `automation_key` and target repository. If none or more than one match, stop. Use `orca automations runs --id <automationId> --json` to select the run whose ID exactly equals `automation_run_id`; verify its `automationId`, repository, and run worktree match `owner.json`. Do not select the latest run as a proxy.
3. Inspect `parent_worktree_id` directly with `orca worktree show --worktree id:<repoId>::<path> --json`. Verify the worktree ID and its `automationProvenance.automationId` and `automationProvenance.automationRunId` match the owner record. Verify its comment contains the exact `run_id`. If `phase` is `locked` and the comment is absent, the matching worktree provenance and IDs still establish the correlation; continue checking for child worktrees and OMP terminals. A comment containing a different token is a conflict; stop and escalate.
4. Inspect the parent run worktree's descendants for Issue worktrees and OMP terminals. For `issue-pr-lifecycle` with non-null `active_issue`, inspect that exact Issue worktree and read its Orca `parentWorktreeId`. If `active_issue.handoff_parent_worktree_id` is present, require an exact match. Read its Issue manifest and require its Issue number, worktree ID, ordered PR list, and handoff run ID to match `active_issue`; for a current-format manifest, also match any handoff Automation run and parent IDs recorded in `active_issue`. Match an available handoff Automation run ID to the exact historical `issue-omp-handoff` run and verify its target repository and `workspaceId` equal the child worktree's parent ID. For legacy records without that ID, identify the unique handoff run by the child worktree's parent ID. If the handoff parent still exists, verify its `automationProvenance` matches the run. Do not require or trust the Issue worktree comment as lifecycle or handoff proof; earlier lifecycle runs may have overwritten it. Inspect terminals in the lifecycle parent worktree and exact Issue worktree with `orca terminal list`, `orca terminal show`, or `orca terminal read`. If Shipping started a merge-when-ready watcher or queue, use its documented Shipping status evidence to prove it is terminal; unclear queue/watcher state means keep the lock. A terminal read that merely shows no recent output is not proof that OMP stopped.
5. Confirm the exact run identified by `automation_run_id` is terminal, and neither `issue-omp-handoff` nor `issue-pr-lifecycle` has a queued or active invocation that could enter this repository workflow after the lock is removed. If `active_issue` is non-null, inspect its current GitHub state, the run's `decisions.tsv`, and the Issue comments. Any `orca:failed` or `orca:human-escalation` state requires a matching verified Issue comment and log row; if either is missing, keep the lock and escalate without claiming recovery is complete. If any run may still be active, its state is unclear, or the CLI cannot establish the state, keep the lock and escalate.

## Release the lock

Release only after the exact owner record, Automation run, and Automation-created parent worktree have been matched; any `active_issue` worktree, OMP terminals, Shipping watcher, and merge queue are confirmed stopped or terminal; both Automations have no queued or active invocation for this repository; and the user explicitly authorizes releasing the lock for this exact repository.

1. Record the exact `run_id`, `automation_run_id`, and `parent_worktree_id` from `owner.json`. Immediately before removal, read `owner.json` again and verify these fields, repository, and phase are unchanged. If any field changed, stop.
2. Remove only `owner.json`, then remove the now-empty lock directory with `rmdir`. Never use recursive removal, wildcards, or a command that deletes a lock by age.
3. If either removal fails, do not try broader cleanup. Report the remaining exact path and escalate.
4. Verify that this exact lock directory no longer exists. Report the repository identity, run token, exact Automation run ID and parent worktree, stop evidence, and verification result.

Do not automatically release abandoned locks, add lock timeouts, or start a replacement Automation as part of recovery. A lock without trustworthy metadata, complete failure/escalation records, or run-state evidence remains in place until a human resolves the ambiguity.
