# ORCA PR lifecycle
Prompt revision: 1

This disabled Automation runs only when a user starts it from the Orca UI. It fetches Issues in `orca:pr-open`, `orca:babysitting`, or `orca:shipping`, then processes one complete Issue stack at a time. A manual Run authorizes Babysit and Shipping for only the Issues in that run's initial snapshot. The state label selects the resume point: new handoffs start at Babysit; interrupted Babysit resumes there; interrupted Shipping resumes at Shipping after verifying no earlier queue is still active. Keep the Automation disabled so the scheduler never starts it.

Never merge PRs outside the selected Issue's verified stack. Never bypass branch protection or required approvals. Never enable GitHub auto-merge for a stack. Shipping must use its documented Graphite merge-when-ready flow. Stop for human intervention when any state, stack membership, worktree, head SHA, reviewer verdict, approval, or merge result cannot be verified.

## Failure and escalation records

Use the installed `show-me-your-work` Skill to initialize an append-only `decisions.tsv` in this Automation run worktree immediately after run provenance is verified and before attempting the lock. Record each lock attempt, Issue snapshot, stack/dependency decision, claim, phase transition, merge result, failure, and escalation with a timestamp and evidence pointer. If the lock cannot be acquired, log that result and do not inspect Issues.

Never change an Issue to `orca:failed` or `orca:human-escalation` without a matching GitHub Issue comment and a log row. First append the log row. Then post the comment with `gh issue comment --body-file` and re-fetch the Issue comments to verify it. Only after the comment is verified, remove any existing `orca:` state labels, add the intended state label, and re-fetch the Issue to verify exactly one `orca:` state label. The comment must include the Automation run ID, Issue number, phase, intended state label, exact blocker and last successful step, evidence (worktree ID, terminal handle, PR URLs and current heads as applicable), and the next safe action or resume phase. If comment or label verification fails, stop the run, append a verification-failure log row, retain the lock, and report the exact problem in the run worktree. Do not process another Issue or release the lock while the failure record is incomplete.

## Run flow

1. Verify this is a manual run of this Automation for the configured target repository. Use `orca worktree current --json` and `orca worktree show --worktree active --json` to verify the run worktree, repository, `automationProvenance.automationId`, and `automationProvenance.automationRunId`. Confirm the exact Automation run record has `trigger: manual`. Initialize the log only after provenance is verified. Stop before reading Issues if any check fails.
2. Acquire the shared repository lock used by `issue-omp-handoff`: `$HOME/.omp/automations/issue-omp-handoff/<canonical-lowercase-repository-with-slashes-replaced-by-underscores>.lock`. Create the parent directory if it does not exist, then use `mkdir` as the atomic operation for the lock itself; do not check the lock path first. If the lock exists or acquisition fails, log the result, do not inspect or change Issues, and stop. Generate `run_id` with `uuidgen`. Write `owner.json` atomically with `run_id`, `automation_run_id`, `parent_worktree_id` (this run worktree ID), `repository`, `automation_key` (`issue-pr-lifecycle`), UTC `acquired_at`, `phase` (`locked`), and `active_issue` (`null`). Read it back and verify every field. Update this run worktree's comment to `Issue PR lifecycle run_id=<run_id>`, verify the comment and Automation run ID, then atomically set `phase` to `admitted`. If a step fails, leave the lock in place and report it. Do not inspect Issues until admission is verified.
3. Fetch each entry label separately with the configured owner/repository, using `state=all`, `--paginate`, and ascending creation time: `gh api --paginate 'repos/<owner>/<repo>/issues?state=all&labels=orca%3Apr-open&sort=created&direction=asc&per_page=100' > pr-open-pages.json`, then repeat with `labels=orca%3Ababysitting` and `labels=orca%3Ashipping`, writing to separate files. Exclude entries containing `pull_request` and combine/deduplicate the page arrays with `jq -s 'add | map(select(has("pull_request") | not)) | unique_by(.number) | sort_by(.created_at)' pr-open-pages.json babysitting-pages.json shipping-pages.json`. Log and snapshot the union once. GitHub may close an Issue before its entire stack merges, so retain `state=all`. If the snapshot is empty, report that and release the verified lock.
4. Before claiming any Issue, re-fetch every snapshot entry. It must have exactly one `orca:` state label, one of the three lifecycle entry states, and the same state recorded in the snapshot. If it has multiple `orca:` state labels, use the required comment-and-log procedure to set `orca:human-escalation` and stop. If it has no state label or a non-lifecycle state, skip it and log the observed change. Validate each remaining Issue's latest handoff manifest and Orca lineage without editing either handoff worktree comment. Accept the current marker `<!-- ORCA PR stack handoff_run_id=<handoff_run_id> automation_run_id=<handoff_automation_run_id> parent_worktree_id=<handoff_parent_worktree_id> -->` or the legacy marker `<!-- ORCA PR stack run_id=<handoff_run_id> -->`. Both manifests must identify the Issue and exact Issue worktree ID and list every PR bottom-to-top with number, URL, base, and head.
5. Verify the manifest against Orca's immutable handoff provenance. Show the exact Issue worktree and read its Orca `parentWorktreeId`. For a current-format marker, require it to equal `handoff_parent_worktree_id` and use the marker's `handoff_automation_run_id`. For a legacy marker, derive the handoff parent ID from the Issue worktree's `parentWorktreeId`. Use `orca automations list --json` and `orca automations runs --id <handoff-automation-id> --json` to identify exactly one `issue-omp-handoff` Automation for this repository and the unique run whose `workspaceId` equals that parent worktree ID; if the marker includes `handoff_automation_run_id`, require an exact run-ID match too. Verify the historical run's target repository and workspace ID. If the parent worktree still exists, verify its `automationProvenance.automationId` and `.automationRunId` against that run. Never use the Issue worktree's mutable comment as proof. Then compare the manifest's ordered PR membership with GitHub: every listed PR must still exist with the same number and URL, and no extra PR may belong to the Issue stack. Require each current PR head branch and the Issue worktree branch to match the manifest's recorded head branches. Treat manifest base branches as handoff-time evidence, not as a requirement for current base branches. Record each PR's current base, head branch, head SHA, and merge state. Before any Babysit action, require every merge state to be known and merged PRs to form a contiguous bottom prefix. For a non-empty unmerged suffix, validate its current topology: its bottom PR may target the configured repository base or the head branch of the last merged PR in the prefix; each higher unmerged PR must target the preceding unmerged PR's head branch. With no merged prefix, this requires the bottom PR to target the repository base and every higher PR to target the preceding PR's head. This rejects an all-open stack whose upper PR has been retargeted to the repository base before Babysit. Escalate an invalid prefix or suffix before step 6 or any OMP interaction. Step 9 must repeat the current-topology check after Babysit pushes. A missing PR, changed membership, changed head branch, mismatched lineage, or unverifiable run requires a verified Issue comment and `orca:human-escalation`; stop without merging.
6. Build a repository-wide dependency graph from the validated snapshot before processing any stack. Each PR head branch must be unique within the snapshot. If a PR's base branch is another snapshotted PR's head branch, that owning Issue must ship first; add a directed dependency edge between the Issues. Ignore within-Issue edges already validated by the manifest order and the pre-Babysit suffix topology check in step 5. A base branch not in the snapshot is acceptable only when it is the configured target base; otherwise its merge dependency is unverified and requires a comment and `orca:human-escalation` on the affected Issue(s). Topologically order Issue stacks by these dependencies and use creation order only to break ties between independent stacks. If head branches are ambiguous or the Issue dependency graph has a cycle, post and verify a comment and log row on every implicated Issue, then stop before Babysit or merge. Never infer PR order from number, date, or list position outside the explicit manifest.
7. Process Issues in the resulting dependency-safe order, one complete Issue stack at a time. Re-fetch the Issue immediately before claim and require its state to match the snapshot exactly; skip and log an Issue whose state changed to a non-lifecycle state. If its state changed to another lifecycle entry state, comment and escalate rather than guessing whether another run advanced it. Record `{number, worktree_id, entry_state, phase: "claiming", handoff_run_id, handoff_automation_run_id, handoff_parent_worktree_id, pull_requests: [{number, url, base, head, sha}, ...]}` in `owner.json.active_issue` atomically. For `orca:pr-open`, transition to `orca:babysitting` and verify it, then set `active_issue.phase` to `babysitting`. For `orca:babysitting` or `orca:shipping`, preserve the label and set `active_issue.phase` to that resume phase. Append the claim/resume decision to `decisions.tsv`. Do not rewrite the Issue worktree comment; it is not lifecycle status. Store lifecycle phases and run IDs in `owner.json` and `decisions.tsv`.
8. If the entry state was `orca:pr-open` or `orca:babysitting`, re-fetch every PR before Babysit. If all PRs are already merged, skip Babysit and continue to step 9 for completion checks. If only some are merged, or merge state is unclear, use the required comment-and-log procedure to set `orca:human-escalation` and stop. Inspect terminals in the exact Issue worktree. Reuse only one OMP terminal confirmed idle and associated with this Issue. If a terminal is live but not idle, or multiple candidates exist, use the required comment-and-log procedure to set `orca:human-escalation` and stop. If none exists, create one with `orca terminal create --worktree <exact-worktree-id> --command omp --title 'PR lifecycle Issue #<number>' --json`, then use `startupTerminal.handle` or re-list the worktree to get its exact handle. Wait for `tui-idle`; send nothing unless Orca reports `satisfied: true`. If readiness remains unconfirmed after one longer wait, close only the new terminal after confirming no prompt was accepted, comment and escalate, and stop. Run pstack Babysit in `drive` mode for the exact frozen stack. It must reach its documented merge-ready stop without merging, arming merge-when-ready, or changing stack topology. A conflict, failed gate, unresolved approval, or any other stop requires a verified comment and `orca:human-escalation`; stop without Shipping.
9. Refresh every PR after any Babysit fix pushes. Compare current membership and head branches with the manifest, record current base branches, head SHAs, and merge states, and confirm merged PRs form a contiguous bottom prefix. If a merged PR appears above an unmerged PR, use the required comment-and-log procedure to set `orca:human-escalation` and stop. For a non-empty unmerged suffix, validate its current topology separately from the original manifest: its bottom PR may target the configured repository base or the head branch of the last merged PR in the prefix; each higher unmerged PR must target the preceding unmerged PR's head branch. Escalate any other base relationship. This accepts a valid retarget of the first unmerged PR to the repository base after its lower predecessor merged, without treating the original manifest as current topology. If this run started at `orca:pr-open` or `orca:babysitting`, replace `orca:babysitting` with `orca:shipping` and verify it; if resuming `orca:shipping`, preserve that label. Update `owner.json.active_issue.phase` and current PR head SHAs atomically, then append the phase decision to `decisions.tsv`. If every PR is merged, continue to step 11 after this phase transition. Otherwise, for a `shipping` resume, inspect the documented Graphite merge-when-ready status before sending anything. If a prior queue is active or its status is unknown, comment and escalate without arming another queue. Inspect the exact Issue worktree's OMP terminals. Reuse only one confirmed-idle terminal; if a terminal is live but not idle or multiple candidates exist, comment and escalate. If none exists, create one and wait for `tui-idle` as in step 8. Send a separate Shipping instruction for this exact stack, naming the verified merged prefix and authorizing work only on the remaining bottom-to-top suffix. The manual UI run authorizes this snapshot only. Shipping must independently verify every PR, merge only the contiguous unmerged suffix from the bottom, use Graphite's documented merge-when-ready flow, and watch the queue through completion. Never use GitHub auto-merge, direct `gh pr merge`, or bypass required checks or approvals.
10. Do not start another Issue while this stack is being reviewed or shipped. If Shipping stops for a failed verdict, human approval, conflict, stalled queue, non-contiguous merge state, or unclear status, use the required comment-and-log procedure to set `orca:human-escalation`, record exact PR states, and stop. Do not release the lock while an OMP terminal, watcher, or armed merge queue started by this run is active or its state is unknown.
11. Only after Shipping reports completion, or step 9 independently verifies the entire stack is already merged, re-fetch every PR and verify all are merged. Stop the Issue's OMP terminal and confirm it is stopped; confirm any Shipping watcher or merge queue is terminal. Then transition the Issue from `orca:shipping` to `orca:completed`, verify exactly one `orca:` state label, append the result to `decisions.tsv`, and clear `owner.json.active_issue` atomically. After every snapshotted Issue has reached `orca:completed` or an explicitly recorded non-lifecycle state, report each Issue and its PRs bottom-to-top.
12. Release the lock only after all OMP terminals and watchers started by this run have stopped, `owner.json` still matches `run_id`, `automation_run_id`, `parent_worktree_id`, repository, and `automation_key`, and `active_issue` is `null`. Remove only `owner.json`, then `rmdir` the now-empty lock directory. Verify its absence. Never steal or recursively remove a lock.

## Issue states

Configure these labels in the target repository before using either Automation. The prompts do not create GitHub labels.

| Label | Meaning |
|---|---|
| `orca:ready` | Eligible for Issue implementation. |
| `orca:queued` | Claimed; child worktree and OMP startup are in progress. |
| `orca:running` | OMP accepted the Issue implementation handoff. |
| `orca:pr-open` | Handoff verified; start Babysit. |
| `orca:babysitting` | Babysit was interrupted; resume Babysit from this phase. |
| `orca:shipping` | Shipping was interrupted; verify prior queue state, then resume Shipping. |
| `orca:completed` | Every PR in the stack is merged and verified. |
| `orca:failed` | A definitive execution failure occurred without a human decision. |
| `orca:human-escalation` | A human decision or intervention is required. |

Keep exactly one `orca:` state label per Issue. Before each transition, re-fetch the Issue, verify the expected state, replace only that state label, then re-fetch and verify the result. Never select only open Issues; GitHub may close an Issue before its upper PRs merge.

## Manual retries

The Automation queries only `orca:pr-open`, `orca:babysitting`, and `orca:shipping`. A `pr-open` Issue starts at Babysit. A `babysitting` Issue resumes Babysit. A `shipping` Issue resumes Shipping after confirming any prior merge queue is terminal. After resolving a `failed` or `human-escalation` blocker, a human must explicitly set the Issue to the correct entry phase and run this Automation again. Use `pr-open` to restart before Babysit, `babysitting` to resume Babysit, or `shipping` to resume Shipping. Do not reset an interrupted Shipping stack to `pr-open`. If the previous run retained the shared lock, use `orca-lock-recovery` after confirming the previous run, OMP terminals, and merge queue are stopped; do not remove the lock manually or start another run while it remains. Never rewrite the handoff worktree comment; lifecycle state belongs in the run log and lock owner record.
